# ブログ再編（えとくらし）

Chihiroさんが書いた下書き・メモ・公開済みの記事を、本人の文体のまま、初めて読む人にも読みやすい記事に組み直す。

このスキルの仕事は**代筆ではなく編集**。
本人はブログを「たっぷり時間をかけて自分の言葉をつむげる」場所として大事にしていて、常連の読者も文体から書き手を感じている。
だから、言葉そのものは書き手のものを使い切り、手を入れるのは主に「並び」「区切り」「つなぎ」「読者への補足」にする。
きれいな文章に書き直したくなっても、本人の口調・ギャグ・叫び・オチが消えたら失敗だと考えること。

## 1. 素材を確かめる

素材は次のどれか。

- チャットに貼られたテキスト、または指定されたファイル
- 公開済みの記事（「id 47 を手直しして」など）→ `posts.py show 47` で読む
- 箇条書きや走り書きのメモ

手を入れる度合いは、指定がなければ「標準」。

| 度合い | やること |
|---|---|
| 軽め | 改行・段落・空行、誤字脱字、明らかな表記揺れだけ |
| 標準（既定） | 軽め＋順番の入れ替え、重複の整理、つなぎの言葉、読者向けの最低限の補足、冒頭と締めの調整 |
| しっかり | 標準＋メモから文章を起こす、構成から組み直す。それでも事実やエピソードは足さない |

素材がメモ・箇条書きなら自然に「しっかり」になる。
「軽く」「ほぼそのまま」「がっつり直して」などの言葉があればそれに合わせる。

## 2. 過去記事を読む

書く前に必ず `references/style-guide.md` を読む。過去48本から抜き出した骨組み・冒頭・締め・改行・語り口・表記・タイトルの傾向がまとまっている。

そのうえで、手本にする過去記事を2〜3本選んで実際に読む。ガイドは要約にすぎず、リズムや温度感は本物の記事からしかつかめないため。
記事の読み書きには `scripts/posts.py` を使う（リポジトリのルートで実行）。

```bash
# 素材のキーワードで近い記事を探す（ヒット数順）
python3 .claude/skills/blog-rewrite/scripts/posts.py search 筋トレ 職場
# 同じカテゴリの最近の記事
python3 .claude/skills/blog-rewrite/scripts/posts.py list --category 仕事 --limit 5
# 直近の記事（今の文体）
python3 .claude/skills/blog-rewrite/scripts/posts.py list --limit 3
# 本文を読む
python3 .claude/skills/blog-rewrite/scripts/posts.py show 39 47
```

選び方の目安：テーマかカテゴリが近いもの1〜2本＋直近の1本。
id 1〜9 は文体が定着する前の記事なので、お手本にしない（理由は style-guide.md の「文体の変遷」）。

過去記事は「調子を合わせる」ための参考で、そこから言い回しを借りてくるためのものではない。
同じ決めゼリフが記事をまたいで繰り返されると、常連の読者には使い回しに見えてしまう。

Python が使えない環境では、posts-data.js を直接 grep して読めばよい（本文の改行は `<br>`）。

## 3. 書く前に骨組みを決める

いきなり書き始めず、まず次の3つを決める。

- **核**：この記事で一番言いたいことを一文で。たいてい原稿の終わりのほうか、一番熱がこもっている箇所にある。
- **読者のつまずき**：初めて読む人が迷う場所。知らない固有名詞や前提、前後した時系列、同じ話の重複、本筋からの脱線。
- **並び**：つかみ → 導入 → 本編 → 気づき → 締め（style-guide.md §2）。原稿のどの部分をどこに置くか。

脱線は削るより、流れを切らない位置（本編の切れ目や締めの直前）に移すほうが、たいていこのブログらしくなる。

## 4. 再編するときの原則

1. **書き手の言葉を使い切る。**
   言い回し・ツッコミ・叫び・オタク語・崩した口調は残す。直すのは順番とつなぎ。
   「標準」なら、原稿の文の大半がそのまま、またはほぼそのまま残っているのが目安。
2. **書いていないことを足さない。**
   事実・エピソード・感情・感想を作らない。足してよいのは接続の言葉（「なので」「そして」「とはいえ」「結果的に」など本人がよく使うもの）と、読者向けの短い補足だけ。
   話の穴が気になったら、本文を埋めずに変更メモで質問する。どうしても本文に置くなら【要確認：〜】と目立たせる。
3. **順番を整える。**
   時系列か、盛り上がっていく順にする。散らばった同じ話題は一か所にまとめる。気づきやまとめは体験のあとに置く。
4. **冒頭は「どうも、〜Chihiroです。」**
   〜には原稿の中の近況や小ネタを使う。原稿にあるもので作れなければ「どうも、Chihiroです。」でよい。
   本文の先頭約100字は検索結果の説明文にもなるので、つかみのあとすぐ、何の話かがわかるようにする。
   思考系の記事や感想羅列など、原稿が本題からいきなり入っているなら無理に足さない。
5. **締めは原稿の一言を活かす。**
   原稿にある締めやオチは、書き手が一番言いたいことであることが多いので、最後に置く。
   締めがなければ、style-guide.md §4 の型から素材に合うものを選ぶ（冒頭への呼び戻しが一番なじみやすい）。
6. **改行と空行。**
   一文一行。段落は2〜5行。小さな区切りは空行1つ、大きな場面転換は空行2つ。ネタバレ・センシティブ注意の直後は空行4つ以上。
   見出し・箇条書き・太字は使わない。項目を並べたいときは「まずは〜」「あとは〜ですね」で段落を立てる。
7. **長すぎる文は分ける。ただしわざとの長さは残す。**
   目安は60字。感情が爆発して読点で畳みかける羅列は、勢いが持ち味なのでそのままにする。
8. **補足は一度だけ、軽く。**
   読者が知らなさそうな略称や固有名詞は、初出で「SBR（ジョジョ七部）」くらいに添える。説明しすぎるとテンポが死ぬ。内輪ネタが通じなくても笑える箇所は、説明しない。
9. **表記は style-guide.md §7 に寄せる。**
   一つの記事の中で揺れている箇所（本当／ほんとう、……／… など）だけ揃える。原稿で一貫しているなら原稿どおり。
10. **長さはおおむね原稿どおり。**
    「標準」で前後2割くらい。重複を削った結果短くなるのはよい。このブログは800〜1500字くらいが中心。

使わない書き方：「いかがでしたか？」「まとめると」「〜と言えるでしょう」「〜することが大切です」といった記事テンプレの言い回し、硬い接続詞（しかしながら・したがって）、絵文字、（笑）。整いすぎた文章は、このブログでは「本人が書いていない」サインに見える。

## 5. 仕上げの見直し

書き終えたら、初めてこのブログに来た人のつもりで頭から読み直し、次を確かめる。

- 誰の・いつの・何の話かが、迷わずわかるか
- 原稿にない事実や感情が混ざっていないか（原稿と見比べる）
- 原稿のお気に入りらしいフレーズ（叫び・オチ・決めゼリフ）が消えていないか
- **公開して大丈夫か**：患者さんや職場が特定されうる情報（看護の仕事の記事はとくに）、家族・友人の実名、住まいがわかる地名、他人の非公開の情報。
  見つけても勝手に消さず、変更メモで知らせて本人に判断してもらう。書く・書かないを決めるのは本人。
- 作品の展開に触れているのにネタバレ注意がないなら、注意書きを入れるか提案する
- 広告・アフィリエイトのリンクがあるなら、posts-data.js に `pr: true` が必要（変更メモで知らせる）

## 6. 出力の形

本文はコードブロックに入れる。チャットのマークダウン表示では、空行のない改行が一行につながり、連続する空行も詰まってしまうため。コードブロックならそのままコピーして使える。

````
## タイトル案
1. 〇〇（おすすめ：理由をひとこと）
2. 〇〇
3. 〇〇

カテゴリ：日常

## 本文
```text
どうも、〜Chihiroです。
（一文一行、空行も記事どおり）
```

## 変更メモ
- 〜の話を前に移動（時系列を揃えるため）
- 〜と〜が同じ内容だったので一つに
- 「〜」に補足を追加
- 【確認】〜（公開してよいか／事実の確認／足りない情報）
````

- 変更メモは3〜7項目くらい。全部の修正を列挙せず、本人が「なぜこうなった？」と思いそうな点を書く。
- 公開済み記事の手直しでは、変更メモに「元の記事からの主な違い」を書く。
- 最後に「posts-data.js に追加（更新）しますか？」と一言添える。

## 7. posts-data.js への反映（頼まれたとき）

頼まれたら、本文をテキストファイルに書き出してスクリプトで反映する。
`<br>` への変換、`"` のエスケープ、次の id の採番、改行コード（CRLF）の維持はスクリプトがやるので、手で posts-data.js を編集しない。

```bash
# 新しい記事（id は自動で次の番号、日付は省略すると日本時間の今日）
python3 .claude/skills/blog-rewrite/scripts/posts.py add --title "秋は飽きない！" --category 趣味 --file /path/to/body.txt --dry-run
python3 .claude/skills/blog-rewrite/scripts/posts.py add --title "秋は飽きない！" --category 趣味 --file /path/to/body.txt

# 公開済み記事の差し替え（日付は指示がなければ変えない）
python3 .claude/skills/blog-rewrite/scripts/posts.py update 47 --file /path/to/body.txt [--title "…"]

python3 .claude/skills/blog-rewrite/scripts/posts.py show 49   # 反映後に読み直して確認
```

- 広告を含む記事は `add` に `--pr` を付ける。
- `add` / `update` のあとは、検索エンジン向けの `sitemap.xml` もスクリプトが自動で作り直す。posts-data.js と一緒にコミットする。
  posts-data.js を手で直したときは `posts.py sitemap` で作り直せる。
- 本文ファイルは一時的な作業用の場所に置き、リポジトリに残さない。
- コミットやプッシュは、ユーザーの指示や作業環境のルールに従う。

## 8. 直しを頼まれたら

「もっと崩して」「ここは元のままで」などの指摘はそのまま反映する。
同じ種類の指摘が2回以上出たら、それはこの書き手の好みなので、`references/style-guide.md` に追記することを提案する。スキルが次から同じ間違いをしなくなる。

## 例

元の原稿（メモ寄りの下書き）：

```text
iPad mini売ってきた！ブックオフで四万円くらいになった、臨時収入ありがてぇ〜！月の自由費が二万円程度なので二か月半ぶんのお小遣い。うへへ。使い道はゆっくり考える。
スマホ断ちは正直続いてない。スマホがあるから。寝る前にスマホ見ると寝つき悪くなる。YouTubeは四時間制限にしてる。だから寝る前は本読んだりなぐり書きしたりしてる。ブルーライトと情報の波、恐るべし。
```

再編（標準）：

```text
どうも、iPad miniをブックオフで売ってきたChihiroです。
なんと四万円くらいになりました。
臨時収入ありがてぇ〜！
月の自由費が二万円程度の私にとっては、二か月半ぶんのお小遣いです。
うへへ、使い道はゆっくり考えようと思います。

正直に言うと、スマホ断ち自体は続いていません。
iPad miniがいなくなっても、手元にはスマホがいますからね。
そして寝る前にスマホを見てしまうと、やっぱり寝つきが悪くなる。
ブルーライトと情報の波、恐るべしです。
なので寝る前は、なるべく本を読んだり、なぐり書きをしたりしています。
```

ポイント：
- 冒頭は原稿の出来事（iPad を売った）から作り、原稿にない形容（「元相棒の」など）は足していない。
- 「ブルーライト〜」を寝つきの話の直後に移し、「だから本を読む」との因果がつながるようにした。
- 「YouTubeは四時間制限」はこの段落の流れから浮くので、スマホの使い方の話として別の段落に回す（例では省略）。
- 「ありがてぇ〜！」「うへへ」「恐るべし」は本人の味なので残した。
